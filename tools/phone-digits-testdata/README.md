# Тестовые данные для поиска по `phoneDigits`

Генератор записей для проверки атрибута `phoneDigits` (ECOSCRM-106) на стенде: лиды, сделки и
контрагенты с телефонами во всех форматах спецификации, в объёме, сопоставимом с продуктивом.

Контракт самого атрибута — в [`docs/phone-digits.md`](../../docs/phone-digits.md), план работ —
в [`docs/plans/20260915-phone-digits-lookup.md`](../../docs/plans/20260915-phone-digits-lookup.md).

## ⚠️ Прочитать до первого запуска

**Создание записей запускает бизнес-процессы.** У `deal-take-to-work-process` и
`crm-lead-process` в определении стоит `ecos:autoStartEnabled="true"` с соответствующим
`ecos:ecosType`, поэтому каждая созданная сделка или лид порождает экземпляр процесса.

15.09.2026 полный прогон на 4200 сделок положил сервис процессов: `citeck_eproc` (предел 2 ГиБ)
получил `OutOfMemoryError`, перестал отвечать через шлюз и оставил около 11 тысяч сообщений
в очереди `bpmn-element-processing-flow`. На трёх записях проблема не проявляется — она видна
только на объёме.

Поэтому перед массовым прогоном **автозапуск надо отключить на стенде**. Отключать именно на
стенде, а не правкой `.bpmn.xml` в репозитории: там описано боевое поведение, и его менять нельзя.

Генератор защищается сам: перед основной работой он создаёт три пробные записи, смотрит,
появились ли у них процессы, удаляет пробы и отказывается продолжать, если процессы стартуют.
Обойти можно флагом `--allow-process-start`, но только осознанно.

## Запуск

```bash
# создать данные и записать файл ожиданий
python3 generate.py generate --expectations expectations.json

# сверить стенд с файлом ожиданий
python3 generate.py verify --expectations expectations.json

# удалить всё, что создал генератор
python3 generate.py cleanup
```

Зависимостей нет, нужен только Python 3. По умолчанию генератор обращается к
`http://localhost` с базовой аутентификацией `admin:admin` — переопределяется флагами
`--url`, `--user`, `--password`.

Объём задаётся флагами `--deals`, `--leads`, `--counterparties`; значения по умолчанию
подобраны так, чтобы на пустом стенде получилось примерно как на продуктиве. Полезен также
`--dry-run`: он собирает весь набор записей и файл ожиданий, не обращаясь к стенду.

## Как это устроено

**Генератор сам знает правильный ответ.** При создании каждой записи он вычисляет ожидаемые
ключи собственным оракулом нормализации и складывает их в файл ожиданий; режим `verify` затем
сверяет стенд с этим файлом.

Оракул — не третья копия контракта. Если он разойдётся с YAML, сверка упадёт, а расхождение
копий алгоритма и есть главный риск задачи. Оракул проверен на 29 случаях спецификации
ECOSCRM-106, включая порядок шагов (разрез строки идёт до извлечения цифр) и дедупликацию.

**Номера синтетические.** Абонентская часть всегда начинается с `0` — такие номера в
российском плане нумерации не выделяются, дозвониться по ним нельзя. Форматы при этом
настоящие, из таблицы примеров.

**Метка.** Все созданные записи несут `ECOSCRM-106-TESTDATA`: сделки и лиды — в `description`,
контрагенты — в `fullOrganizationName` (у типа контрагента нет ни `name`, ни `description`).
По ней работает `cleanup`, и по ней же можно отличить сгенерированное от настоящего.

## Что покрывают данные

| Блок | Записей | Содержание |
|---|---|---|
| Сценарный | 60 | все форматы таблицы; комбинации источников (`phone` / `contacts` / оба совпадают / оба расходятся / ни одного); пять контактов; два номера в одной строке; семь вариантов добавочного и три разделителя; девять значений, обязанных дать пустой массив |
| Коллизии | 5 | один ключ на трёх сделках; один ключ на сделке и лиде |
| Связанные | 8 | контрагент с четырьмя сделками и лидом **без собственных телефонов** — достижимы только через контрагента; отдельно контрагент, чей номер продублирован в контактах его же сделки |
| Массив | остальное | распределение по продуктиву: 28 % сделок заполняют устаревшее `phone`, лиды его не имеют вовсе |

`verify` выполняет четыре группы проверок: ожидаемые ключи у каждой сценарной записи, поиск по
каждому ключу, коллизии (возвращаются **все** записи с ключом), двухшаговый поиск COREDEV-510
(контрагент по ключу → `in counterparty [...]`, затем объединённый `or(...)` с требованием
вернуть запись ровно один раз) и поиск по несуществующему ключу.

## Особенности стенда, на которые уходит время

- **Сделке и лиду обязательно задавать `manager`.** Без него вычисляемая роль отдаёт
  `GROUP_crm-manager`, администратор в эту группу не входит, и запись становится невидимой для
  своего же создателя: `records_mutate` отвечает `ok: true`, запись появляется в таблице, но
  чтение возвращает пустые значения, а `records_query` её не находит.
- **Контрагенту `_workspace` не нужен** (у существующих он `null`), но нужны
  `counterpartyType`, `counterpartyKind` и названия организации.
- **Аутентификация — базовая.** Раздел про OIDC в `workspace-ctk/docs/records-api-auth.md` к
  этому стенду неприменим: token endpoint отдаёт 404.
- **Предикат для поиска по `phoneDigits` ecos-data строит через оператор перекрытия `&&`**, а не
  `@>`. При снятии `EXPLAIN` вручную надо использовать именно `&&`, иначе план будет не тот,
  что выполняется в действительности.
