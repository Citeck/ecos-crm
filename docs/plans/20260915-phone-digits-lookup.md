# phoneDigits: поиск лида, сделки и контрагента по номеру телефона

Задача в трекере: [ECOSCRM-106](https://citeck.ecos24.ru/v2/dashboard?recordRef=emodel/ept-issue@ECOSCRM-106). Потребитель результата — COREDEV-510 (маршрут «запись разговора Mango Office → транскрибация → активность»).

## Overview

Чтобы по входящему номеру телефона находить лид или сделку, номер должен лежать в проиндексированной колонке в нормализованном виде. Сейчас телефон хранится в JSON-атрибуте `contacts[].contactPhone` и в скалярных полях контрагента, а предикатный поиск по содержимому JSON в ecos-data невозможен: путь `contacts.contactPhone` срезается в `alwaysFalse` и запрос молча возвращает ноль записей. Проверено на живых данных и для лида, и для сделки.

Решение: вычисляемый атрибут `phoneDigits` (TEXT, multiple, GIN-индекс) на типе `opportunity` (его наследуют `lead` и `deal`) и на типе `ecos-counterparty`. Значение — массив уникальных ключей по 10 цифр, полученных из всех телефонов записи одним и тем же алгоритмом нормализации.

Что это даёт:

- COREDEV-510 получает рабочий двухшаговый поиск: сначала контрагент по его `phoneDigits`, затем сделка по `OR(eq phoneDigits, in counterparty [refs])`, затем лид;
- пользователь впервые получает рабочий фильтр «Телефон» в журналах лидов и сделок — сейчас он молча не работает по той же причине.

**Симметрия — главное требование.** Один и тот же алгоритм применяется в трёх местах: скрипт на `opportunity`, скрипт на контрагенте и нормализация номера из события Mango в COREDEV-510. Расхождение хотя бы в одном шаге означает, что ключи не совпадут и поиск будет молча промахиваться. Спецификация алгоритма — в описании ECOSCRM-106, раздел «Нормализация номера».

## Принятые решения

Эти решения приняты при планировании и в ходе реализации не пересматриваются без явного согласования.

1. **Один план на оба репозитория.** Задачи явно указывают файлы и в `ecos-crm`, и в `ecos-datalist`. Причина: алгоритм нормализации пишется один раз и сразу согласованно в двух местах — расхождение между ними и есть главный риск задачи.
2. **Заполнение существующих записей — декларативными патчами**, а не ручным запуском действия. Патч отрабатывает автоматически на каждом стенде, и приёмку можно проверить автоматически.
3. **Скрипт остаётся на JS в YAML, а не на Java в микросервисе.** Выбора практически нет: модель типов другого способа не даёт. Реализация на Java означала бы слушатель `DbRecordChangedEvent`, а он (а) живёт внутри `ecos-model` — ядра платформы, где CRM-логике не место, отдельного микросервиса под CRM сейчас нет; (б) требует защиты от рекурсии, потому что запись меняется из слушателя её же изменения; (в) делает запись асинхронной — появляется окно, в которое звонок не найдёт сделку; (г) лишает нас штатного пересчёта, потому что «Обновить вычисляемые атрибуты» работает именно с computed-атрибутами, и заполнение существующих записей снова пришлось бы делать патчем на Kotlin.
4. **Модульные тесты — `mvn test` на настоящем GraalJS**, в maven-профиле с активацией по `<jdk>[17,)</jdk>`. Тест читает `config.fn` прямо из YAML, поэтому эталонную копию алгоритма вести не надо: единственный источник правды — сам YAML. Профиль нужен потому, что версия JDK на агенте Jenkins неизвестна, а сломать общую сборку нельзя.
5. **Колонка «Телефон» в журналах чинится в этом же плане**, отдельной задачей в конце.
6. **Порядок — TDD.** Таблица примеров в ECOSCRM-106 уже является готовой спецификацией, её можно перенести в тест до написания скрипта.

## Testing Strategy

- **Модульные тесты** — обязательны в каждой задаче, где меняется скрипт или модель. Прогоняются на GraalJS, читая `config.fn` из YAML.
- **Приёмка на стенде** — обязательный и блокирующий этап, а не дополнение. Проверяется через Records API (Citeck MCP: `records_query`, `records_mutate`) и через Playwright для интерфейсной части.
- **Покрываем не только успешный путь.** Обязательно: альтернативные ветки (номер только в `contacts`; номер только в `phone`), негативные (короткий номер, строка без цифр, пустые контакты), краевые (12+ цифр, добавочный после запятой, дубликаты), повторяемость (повторный прогон патча ничего не ломает).
- Ветка поиска через контрагента на текущих данных почти не срабатывает (контрагент заполнен у 2% сделок и 6% лидов), поэтому проверяется **только на подготовленных записях**, созданных в рамках приёмки.

и «Плагин недоступен» из той же серии.

Для следующего, кто будет проверять журналы: открывать их надо в рабочем пространстве CRM
(`ws=crm-workspace`), иначе журнал пуст — в личном пространстве администратора записей нет.

**Как разбирали последствия — и что из этого пригодится следующему.**

Восстановление заняло около часа и потребовало трёх заходов. Полезны не столько команды,
сколько два свойства инструментов, которые сбивали с толку и стоили неверных выводов:

- **`purge_queue` удаляет только готовые сообщения.** Если потребитель жив, он уже забрал
  их себе, и в очереди `ready = 0`, а `unacknowledged` равно всему объёму — чистка в этом
  случае не делает ничего. Правильный порядок: остановить потребителя, дождаться возврата
  сообщений в готовые, чистить, затем запускать. Я от этого порядка отступил и трижды
  впустую выполнил команду, решив по счётчику, будто она срабатывает частично.
- **Management API RabbitMQ (`:15672/api/queues`) отдаёт кешированную статистику.** Живые
  числа даёт только `rabbitmqctl list_queues name messages messages_ready
  messages_unacknowledged`. Несколько противоречивых замеров подряд, где одна и та же
  очередь показывала то 0, то 21241, объясняются именно этим.
- **Показатель глубины очереди без показателя живости потребителя не интерпретируется.**
  Замершая очередь при живом сервисе означает равновесие, при мёртвом — что он умер; в
  цифрах это выглядит одинаково. Я дважды прочитал вторую ситуацию как первую. В наблюдение
  надо с самого начала включать проверку доступности сервиса через шлюз.

Очереди, участвующие в каскаде: `bpmn-process-async-start-process` (команды «запустить
процесс»), `bpmn-element-processing-flow` (шаги уже запущенных процессов) и выше по потоку
`eproc` (события о созданных записях, из которых и берутся старты). Чистка только очереди
стартов не помогает: она наполняется заново из `eproc`, а уже запущенные экземпляры
продолжают порождать шаги независимо от неё.

**Чем кончилось.** Рабочая последовательность, приведшая стенд в порядок:

1. `docker stop citeck_eproc_...` — потребитель остановлен, все невподтверждённые сообщения
   вернулись в готовые (проверено: `ready` стало равно полному объёму, `unacknowledged` — 0);
2. `rabbitmqctl purge_queue bpmn-process-async-start-process` — источник каскада убран,
   312 → 0. Та же команда при живом потребителе не делала ничего;
3. `docker start citeck_eproc_...` — оставшиеся 5304 элемента разобрались за несколько минут,
   потому что подпитки новыми стартами уже не было.

Итог: все очереди `bpmn-*` пусты (кроме 5 сообщений в `-dlq`, лежавших там до генерации),
eproc отвечает, CPU 2 % против прежних 700–900 %, `OutOfMemoryError` нет. Три признака
сошлись одновременно — именно этого совпадения не было в прошлые разы, когда «спокойствие»
означало смерть сервиса.

Что потеряно: 312 процессов, которые не стартовали, и часть шагов у запущенных экземпляров
синтетических сделок. Проверено выборками (480 сообщений из очереди элементов и 60 из
очереди стартов): все до единого относились к `deal-take-to-work-process` на записях с
меткой генератора, чужих процессов среди них не было. Данные `phoneDigits` не затронуты —
они живут в `emodel`, который ни разу не пострадал.

### Прогон дозаполняющего патча на полном объёме

Последний пункт Task 11. Прогон сделан 15.09.2026 на стенде `tdcuosa`, на тех же 5783 записях
(4325 сделок, 932 лида, 526 контрагентов), на которых закрыты остальные критерии.

**Как обеспечена наблюдаемость.** Групповое действие `update-calculated-atts` сохраняет запись
только если пересчитанное значение отличается от текущего (`recomputeAttsAndSave`). На стенде все
значения уже верные, поэтому успешный прогон и прогон, не дошедший до записей, дали бы одинаковый
результат: `APPLIED`, ноль ошибок, совпадающие контрольные суммы. Поэтому перед прогоном 200
значений намеренно заменены в базе на заведомо неверное `{0000000001}` — 100 сделок (по 50 с
каждого конца диапазона идентификаторов, чтобы проверить не только первую страницу обхода),
50 лидов, 50 контрагентов. Приём тот же, что в Task 7, но на объёме вместо одной записи. Перед
порчей снят полный снимок всех 5783 значений, чтобы восстановление не зависело от патча.

**Ход прогона.** Дата в обоих файлах патчей поднята до `2026-09-15T18:00:00Z`, оба проекта
пересобраны (`mvn clean package -DskipTests`, `BUILD SUCCESS`), зипы выложены в каталог
`ecos-apps` стенда в 14:57:45 UTC. Артефакты патчей развернулись в 14:57:53, исполнение
запустилось в 14:58:05.

| Патч | Записей в выборке | Длительность | Ошибок |
|---|---|---|---|
| `fill-counterparty-phone-digits` (`ecos-counterparty`) | 526 | 3,535 с | 0 |
| `fill-opportunity-phone-digits` (`opportunity` → `deal` + `lead`) | 5257 | 30,595 с | 0 |

5257 = 4325 сделок + 932 лида, то есть групповое действие по `opportunity` действительно дошло до
обоих наследников. Предикат `not empty dateReceived` не отсёк ничего: `dateReceived` заполнен у
всех записей стенда. Пропускная способность — около 172 записей в секунду.

**Результат.** Все 200 испорченных значений восстановлены. Снимки всех трёх таблиц после прогона
побайтово совпали с базовыми, `phoneDigits IS NULL` не появился нигде. В журнале `emodel` за окно
прогона нет ни одной строки уровня ERROR или исключения. Очереди `bpmn-*` остались пустыми
(кроме пяти сообщений в `-dlq`, лежавших там до прогона), память и загрузка `eproc` не выросли —
история с автозапуском процессов на массовой мутации не повторяется, потому что автозапуск
привязан к созданию записи.

Отдельно проверено, что пересчёт **не** выглядит как правка пользователя: ни у одной сделки
`__modified` не изменился, хотя 100 значений были переписаны. Для истории изменений и для
сортировок по дате правки это правильное поведение, но означает, что по `__modified` факт
прогона патча отследить нельзя.

⚠️ **Главное, что выяснилось, и что важнее самих цифр: `ecos_patch` сообщает `APPLIED` задолго до
того, как пересчёт закончен.** Патч типа `mutate` только создаёт групповое действие и сразу
рапортует `completed: true`, `durationMs: 14`. Реальная работа идёт асинхронно в пуле
`group-actions-*`: на `opportunity` — ещё 30,6 секунды после того, как запись патча стала `APPLIED`.
Отсюда два следствия для выкладки на прод:

- `durationMs` в `patchResult` не является временем дозаполнения и не годится для оценки. Смотреть
  надо строку `Group action status changed from 'RUNNING' to 'COMPLETED'` в журнале `emodel`;
- запись группового действия не хранится в базе `emodel` (таблицы для неё нет, а чтение
  `emodel/group-action@<id>` после завершения возвращает пусто). Значит, перезапуск `emodel`
  в это окно оставил бы патч в состоянии `APPLIED` с незавершённым пересчётом и без
  автоматического повтора: патч сам по себе повторно не запускается, дату пришлось бы поднимать
  вручную. Сценарий «перезапуск ровно в это окно» не воспроизводился, вывод сделан по отсутствию
  хранилища у группового действия.

**Проверка через Playwright на восстановленных данных.** Журнал сделок: поиск по ключу
`4950060575` вернул ровно одну запись — Сделку №2233, в колонке «Телефон» человекочитаемое
`+7-495-00605-75`, то есть нормализация нашла номер, записанный в нестандартном формате. Журнал
лидов: поиск по `4950490248` вернул Лид №803 — одну из 50 намеренно испорченных записей, то есть
восстановленное значение попало и в индекс, и в выдачу. Негативная ветка: поиск по
несуществующему ключу `0000000001` (тому самому, которым портились значения) даёт аккуратное
пустое состояние «Нет данных / Нет элементов в списке» без ошибки. Ни одного запроса 4xx/5xx,
относящегося к сделкам, лидам или контрагентам; вёрстка, локализация и содержимое ячеек без
замечаний.

➕ Замечено попутно, к `phoneDigits` отношения не имеет: на каждой странице журнала падает с
HTTP 500 запрос `records/query?k=q_integrations_import_data_variant`, в консоли — `App is not
available: 'integrations'` и всплывающее «Плагин недоступен». На стенде не развёрнут микросервис
`integrations`, но отсутствие необязательного приложения даёт пользователю 500 и ошибку в консоли
вместо тихой деградации. Также один раз ответил 500 `gateway/ai/api/assistant/availability`, при
повторных загрузках — 200.

**После прогона стенд возвращён в исходное состояние:** даты в обоих файлах патчей откачены
(`12:00:00Z` для `opportunity`, `00:00:00Z` для контрагента), проекты пересобраны и выложены,
записи патчей на стенде снова стоят с исходными датами и `APPLIED`, данные побайтово совпадают
с базовым снимком. Попутно подтверждено, что выкладка артефакта с **меньшей** датой перезаписывает
дату в записи патча, но статус не сбрасывает, — то есть понижение даты тихо меняет то, что потом
будет считаться «прежней» датой при сравнении.


✅ **Закрыт вопрос «каким механизмом пересчитались существующие записи».** Ранее здесь было
записано наблюдение: сделка №96 (заполнен только `phone`, контактов нет) получила ключ после
переразвёртывания, «хотя дату дозаполняющего патча никто не менял», и отсюда делался вывод, что
пересчёт запускает изменение определения типа. **Наблюдение было ошибочным: дату меняли.** Коммит
`babcaa1` поднимает `date` в `fill-opportunity-phone-digits.yml` с `2026-09-15T00:00:00Z` до
`12:00:00Z` — ровно ради добавленного источника `phone` и нового предиката; в записи патча на
стенде стоит та же дата `12:00`, статус `APPLIED`, время применения 13:16 UTC. То есть сделка №96
получила ключ штатным перезапуском патча, никакого второго механизма нет.

Проверка по коду это подтверждает независимо от стенда. Пересчёт вычисляемых атрибутов живёт
только в пути мутации записи: `ComputedAttsService.computeAttsToStore` вызывается из
`DbRecordsMutateDao.mutateImpl`, и `ON_MUTATE` пересчитывается при каждом сохранении записи.
Слушатели изменения типа (`TypesServiceImpl`, потребитель — `TypesConfig.init`) только
перерегистрируют DAO под новый sourceId и данных не трогают. Добавление нового атрибута в тип
доходит до `DbDataServiceImpl.ensureColumnsExistImpl`, а это чистый DDL `ALTER TABLE ADD COLUMN`
без дозаполнения. Пути «вычислить при чтении и сохранить» не существует вовсе: `DbRecord` отдаёт
то, что лежит в колонке. В `ecos-data` это зафиксировано тестом
`DbRecordsComputedAttsTest.computedAssocTest`: после переразвёртывания типа с новым вычисляемым
атрибутом у ранее созданной записи значение остаётся пустым, пока не выставят
`__updateCalculatedAtts`; соседний `updateCalculatedAttsUpdatesDisplayName` показывает то же самое
для `dispNameTemplate`.

**Что из этого следует для релиза.** Единственный способ дозаполнить существующие записи —
групповое действие `update-calculated-atts`, то есть наш патч, и запускается он только при
увеличении даты. Значит, увеличение даты в релизе обязательно, иначе 1213 продуктивных сделок
с заполненным только `phone` ключей не получат. В `babcaa1` дата уже поднята до `12:00:00Z`,
и этого достаточно: на стендах, где применялась первая версия патча, сохранена дата `00:00:00Z`,
а `EcosPatchConfig` сбрасывает статус в `PENDING` при любой более поздней дате. Отдельно
проверять на проде нужно не статус патча, а завершение группового действия — см. предупреждение
про асинхронность выше.

### Task 12: Ключ с кодом страны (E.164) вместо десяти цифр

Задача добавлена 15.09.2026, после того как план был закрыт во второй раз. Основание —
вопрос «почему номер без кода страны» и следом «может быть много номеров из СНГ». План снова
возвращён в активные, потому что правку надо внести **до выкладки `phoneDigits` на промышленный
стенд**: после выкладки придётся пересчитывать уже боевые ключи и менять маршрут Mango, который
к тому времени будет работать.

**Замер, из-за которого решение изменилось.** Прежний вывод «иностранных номеров единицы»
держался на предположении, а не на данных. Прямой запрос к продуктиву (только чтение,
профиль `production`) показал:

| Источник | Номеров СНГ | Из чего |
|---|---|---|
| `deal.phone` | 46 | Узбекистан, Таджикистан, Азербайджан, Беларусь, Киргизия, Украина |
| `ecos-counterparty.phone` / `cellPhone` | 0 | все десять кандидатов оказались российскими номерами, внутри которых встречается тройка вроде `374` или `995` |

46 — это 3,8 % от 1213 сделок с заполненным `phone`, и это **нижняя оценка**: основной источник
`contacts[].contactPhone` лежит в JSON, а предикатом по нему не посчитать — ровно та проблема,
из-за которой задача и появилась. Доля по контактам не измерялась.

**Что не так с правилом «последние 10 цифр».** Для двенадцатизначного номера СНГ оно оставляет
последнюю цифру кода страны и девять национальных: `+375 29 940 71 02` → `5299407102`. Ключ
работает только потому, что обе стороны считают его одинаково, то есть ошибаются согласованно.
Отсюда два следствия:

- ключ нельзя сверить ни с чем за пределами этой замкнутой пары. Любой четвёртый потребитель,
  посчитавший ключ очевидным способом (в E.164), будет молча промахиваться;
- ⚠️ **столкновение с российскими номерами выглядит настоящим.** Ташкентский городской
  `+998 12 XXX XX XX` — двенадцать цифр, ключ `812XXXXXXX`. Петербургский `+7 812 XXX-XX-XX` —
  одиннадцать цифр, ключ `812XXXXXXX`. Форма совпадает полностью. Это вывод по планам нумерации,
  а не измерение: в данных такую пару не искали, потому что `phoneDigits` на продуктив ещё не
  выложен и сверять нечего. **Проверить до выкладки.**

**Решение: ключ — номер в E.164, то есть все цифры вместе с кодом страны.** Таблица кодов стран
при этом не нужна, страну определять не требуется. Разворачивается только российский
междугородний префикс, и делается одно допущение для номера, введённого без кода страны:

1. меньше 10 цифр — ключа нет (как было);
2. **больше 15 цифр — ключа нет.** 15 — максимум по E.164, то есть значение длиннее просто не
   является номером. Новый пункт, он же чинит склейку номеров, разделённых пробелом (см. ниже);
3. ровно 10 цифр — приписать `7` (единственное допущение «по умолчанию Россия»);
4. 11 цифр с ведущей `8` — заменить ведущую на `7`;
5. иначе оставить все цифры как есть.

Почему именно так, а не «приписывать `7` российским номерам»: определить, что номер российский,
по длине нельзя. В данных продуктива лежит `+38050215956` — одиннадцать цифр, украинский номер,
введённый с ошибкой. Правило «одиннадцать цифр, значит российский» превратило бы его в
российский; правило из пункта 4 не срабатывает (ведущая цифра `3`, не `8`) и оставляет номер
собой.

⚠️ **Меняется поведение на документированном краевом случае — два номера, разделённые пробелом.**
Сейчас склейка обрезается до последних десяти цифр, и последний номер случайно находится
(`+7 495 556-45-95 и 8 916 117-77-16` → `9161177716`), а в другом случае получается ключ,
которого нет ни у кого (`+7 495 556-45-95 и 630-20-10` → `5956302010`). После правки обе склейки
превышают 15 цифр и **не дают ключа вовсе**. Находимость последнего номера теряется, зато
пропадает ложный ключ. Для поиска по входящему звонку «не нашли» безопаснее, чем «нашли не то».
Это ровно то лечение, которое раздел «Ограничения» и предлагал — отбрасывать куски, где цифр
заметно больше одиннадцати.

**Цена правки:** меняются все ключи, поэтому нужен пересчёт всех записей (поднятие даты обоих
патчей) и синхронная правка третьей копии алгоритма в маршруте Mango (COREDEV-510). Пока
развёрнута одна сторона из двух, поиск молча не находит ничего.

⚠️ **Последствие для пользователя:** в фильтр «Телефон» в журналах теперь вводится одиннадцать
цифр с ведущей `7` вместо десяти. Ергономика хуже; вопрос о нормализации вводимого значения на
стороне `ecos-ui` уже стоит в Post-Completion и становится заметно весомее.

## Technical Details

**Формат значения.** Массив уникальных строк по 10 цифр. При отсутствии годных номеров — пустой массив, никогда не `null`.

**Алгоритм нормализации** (полная спецификация с таблицей примеров — в ECOSCRM-106, порядок шагов менять нельзя):

1. пустое значение — пропуск;
2. разрезать по разделителям `,` `;` `#` `/`, перевод строки, а также `доб`, `доп`, `вн` (точка необязательна) и `ext` (регистр не важен) — **до** извлечения цифр;
3. каждый кусок обрабатывается независимо;
4. удалить всё, кроме `0-9`;
5. меньше 10 цифр — ключа нет;
6. взять последние 10 цифр;
7. дедупликация в пределах записи.

**Ограничения GraalJS, которые определяют, как писать скрипт:**

- ⚠️ **Исправлено по итогам Task 1 — исходное утверждение плана не подтвердилось.** Планировалось, что методы `Array.prototype` на загруженных значениях недоступны. Прогон на настоящем GraalJS 24.2.2 показал обратное: `value.load(...)` действительно отдаёт `java.util.ArrayList` и `LinkedHashMap`, но опция `js.foreign-object-prototype` в этой версии включена по умолчанию, а платформа её не выключает — единственная настройка контекста в `EcosScriptsInitializer` (ecos-webapp-lib) это `js.nashorn-compat`, и она выключена. Поэтому загруженный список для скрипта — полноценный массив: `Array.isArray` даёт `true`, `map`, `filter`, `indexOf`, `join` работают. Поведение зафиксировано тестом `ComputedScriptRunnerTest.loadedMultipleAttributeBehavesAsAnArray`, чтобы смена версии GraalJS не прошла незамеченной.
- ⚠️ **А вот это ограничение настоящее, найдено там же:** у загруженного JSON-объекта (`LinkedHashMap`) чтение по ключу работает, а `Object.keys(obj)` возвращает пустой список — перебрать поля объекта нельзя, обращаться можно только к заранее известным именам. Зафиксировано тестом `loadedJsonObjectIsReadableByKeyButNotEnumerableByObjectKeys`.
- Стиль из решения по Task 2 остаётся в силе: перебирать обычным `for (var i = 0; i < arr.length; i++)`, результат собирать в литерал `[]` через `push`. Это работает при любом значении `js.foreign-object-prototype`, то есть не зависит от версии GraalJS на стенде.
- Обёртка скрипта в `(function(){…})()` ставится, только если в тексте есть подстрока `"return "` — с пробелом. `return[...]` не сработает.
- Массив доезжает до колонки без схлопывания, но держится это на поэлементной обработке в `RecordComputedAttsService.convertResult`: `mapAttributeTypeToRecordComputedResType` для TEXT выдаёт `RecordComputedAttResType.TEXT` и про `multiple` не знает. Поэтому Task 1 и Task 2 проверяют именно возврат массива, а не только отдельные ключи.

**Источники номеров:**

- `opportunity` — только `contacts[].contactPhone`. Депрекированное `deal.phone` **не** источник: оно заполнено у 1213 из 4280 сделок, но в выборке 40 записей во всех случаях дословно совпадает с `contacts[0].contactPhone`, то есть уже зеркалировано. ⚠️ Ревью после реализации эту посылку не подтвердило: на стенде у сделок с заполненным `phone` список `contacts` пуст, ключей нет вовсе. Пункт вынесен в Post-Completion на перепроверку;
- `ecos-counterparty` — `phone`, `cellPhone` и `contacts[].contactPhone`, все три сливаются в один массив;
- скрипт на `opportunity` **не** читает `counterparty.phoneDigits` — иначе вернётся проблема устаревания значения.

**Осторожно при замерах:** предикат `empty` на JSON multiple считает пустой массив `[]` непустым, поэтому доли заполненности контактов измеряются только выборкой, а не счётчиком.

**Про сборку при живом стенде:** общее правило запрещает запускать `mvn` в рабочем дереве с поднятым стендом. Здесь риск минимален — оба проекта собирают только zip с артефактами и не поднимают Spring, — но если в том же дереве работает другая сессия, о сборке нужно договориться.

- **сразу после выкладки убедиться, что патч не отработал вхолостую.** Патч `fill-opportunity-phone-digits.yml` имеет тип `mutate` и пустой `dependsOnRefs`, то есть его выполнение не упорядочено относительно выкладки `opportunity.yml`. Если он выиграет гонку, он завершится успешно и не заполнит ничего, а сам по себе повторно не запустится. Проверка — запрос числа записей, у которых телефон есть, а `phoneDigits` пуст; если такие есть, поднять `date` в патче и выложить заново.

  контрагента с тремя источниками. Атрибут объявлен только у `deal`; у лида `value.load('phone')`

  `phone` у лида. ⚠️ Предупреждение в COREDEV-510 «номер только в `deal.phone` не найдётся» больше не
  действует и должно быть снято в комментарии к задаче;
- колонка «Телефон» показывает `contacts.contactPhone`, а фильтрует по `phoneDigits`, куда после
  добавления второго источника попадают и ключи из депрекированного `deal.phone`. У сделок, ради которых
  источник и добавлялся (номер в `phone`, `contacts` пуст), фильтр вернёт строку с пустой ячейкой
  «Телефон»: совпадение есть, показать нечего, и причина пользователю не видна. Обратное расхождение —
  номер в `deal.phone`, который в колонке не показывается никогда, — тоже остаётся. Варианты: выводить
  в колонке `contacts.contactPhone` с запасным значением `phone` либо оставить как есть и описать
  расхождение в подсказке к колонке. Решение человека;
- в расширенном фильтре журнала по колонке «Телефон» условия, отличные от «содержит», «равно» и «один из», молча выбрасываются из запроса: `DbEntityRepoPg` умеет строить SQL по multiple-колонке только для `eq`, `contains` и `in`, на остальных возвращает `false`, и предикат исчезает из выражения. Пользователь при этом получает **весь список**, а не пустой — до правки та же колонка давала `alwaysFalse` и ноль записей, то есть направление ошибки поменялось на противоположное. Надо решить, ограничивать ли набор условий у колонки или чинить это на стороне платформы;
- у длины куска нет верхней границы, а `*` не входит в список разделителей. Значение вида `8-495-556-45-95*422` или `8-495-556-45-95 (422)` даёт один кусок из четырнадцати цифр, последние десять которых (`5564595422`) не принадлежат никакому абоненту: настоящий номер теряется, а придуманный ключ может совпасть с ключом чужой записи. Лечится либо добавлением `*` в разделители, либо отбрасыванием кусков, где цифр больше двенадцати. Сюда же относится найденная третьим проходом ревью табуляция: `\r` и `\n` в списке разделителей есть, `\t` — нет, поэтому `"+7 916 117-77-16\t+7 495 123-45-67"` даёт единственный ключ `4951234567` и теряет первый номер. В отличие от пробела, у табуляции нет довода против: внутри номера её не ставят, а значения из таблиц и выгрузок CSV разделены именно ею. Трогать это местной правкой нельзя: алгоритм обязан совпадать во всех трёх копиях, поэтому изменение вносится сразу в `opportunity.yml`, `ecos-counterparty.yml`, маршрут Mango COREDEV-510 и `docs/phone-digits.md`;
- фильтр по телефону на канбан-досках сделок и лидов не работает: подмену атрибута по `searchConfig.searchAttribute` делает `JournalsConverter.searchConfigProcessed`, вызывается она только из `journalsDataLoader`, а `sagas/kanban.js` строит предикат мимо неё. Доски ссылаются на те же журналы, поэтому в них уходит `contacts.contactPhone` и результат пуст. Это правка в `ecos-ui`, отдельной задачей.
