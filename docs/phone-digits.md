# phoneDigits — поиск лида, сделки и контрагента по номеру телефона

Вычисляемый атрибут `phoneDigits` хранит нормализованные ключи всех телефонов записи и
позволяет найти её по входящему номеру звонка. Этот файл — контракт: всё, что нужно знать
внешнему потребителю (в первую очередь маршруту Mango Office из
[COREDEV-510](https://citeck.ecos24.ru/v2/dashboard?recordRef=emodel/ept-issue@COREDEV-510)),
чтобы считать ключ ровно так же и находить записи.

Задача, в рамках которой поле заведено, — [ECOSCRM-106](https://citeck.ecos24.ru/v2/dashboard?recordRef=emodel/ept-issue@ECOSCRM-106).
История реализации и результаты приёмки — в `docs/plans/20260915-phone-digits-lookup.md`.

## Зачем поле понадобилось

Телефон в CRM хранится в JSON-атрибуте `contacts[].contactPhone`, а предикатный поиск по
содержимому JSON в `ecos-data` невозможен: путь `contacts.contactPhone` срезается в
`alwaysFalse`, и запрос **молча возвращает ноль записей**, не ошибку. Номера при этом введены
в произвольном формате. `phoneDigits` решает обе проблемы сразу: это отдельная
проиндексированная колонка с приведёнными к единому виду значениями.

## Где объявлено

| Тип | Файл | Источники номеров |
|---|---|---|
| `opportunity` (наследуют `lead` и `deal`) | `ecos-crm/src/main/resources/app/artifacts/model/type/opportunity.yml` | `phone` (депрекированное, есть только у `deal`), `contacts[].contactPhone` |
| `ecos-counterparty` | `ecos-datalist/src/main/resources/app/artifacts/model/type/ecos-counterparty.yml` | `phone`, `cellPhone`, `contacts[].contactPhone` |

Параметры атрибута в обоих типах одинаковы: `type: TEXT`, `multiple: true`,
`computed: { type: SCRIPT, storingType: ON_MUTATE }`, `index: { enabled: true }`.

Собственной таблицы у `opportunity` нет — записи лежат в таблицах наследников, поэтому колонок
и GIN-индексов три, а не два (схема `ecos_data` базы `citeck_emodel`):

```
ecos_data.t_lead                "phoneDigits" varchar[]   t_lead_phoneDigits_idx                USING gin ("phoneDigits")
ecos_data.t_deal                "phoneDigits" varchar[]   t_deal_phoneDigits_idx                USING gin ("phoneDigits")
ecos_data.t_ecos_counterparty   "phoneDigits" varchar[]   t_ecos_counterparty_phoneDigits_idx   USING gin ("phoneDigits")
```

Индекс создаётся платформой только при явном `index: { enabled: true }` — ручной DDL не нужен,
но и без флага его не будет.

## Формат ключа

Ключ — строка **ровно из десяти цифр**, без плюса, скобок, пробелов и кода страны.
Значение атрибута — массив уникальных ключей по всем телефонам записи. Если ни одного годного
номера нет, значение — **пустой массив, никогда `null`**.

## Алгоритм нормализации

Вход — одна произвольная строка. Выход — ноль, один или несколько ключей.
**Порядок шагов менять нельзя.**

1. **Пустое значение** (`null`, пустая строка, строка из пробелов) — пропуск.
2. **Разрезать по разделителям — до извлечения цифр.** Разделители, регистр не важен:
   `,` `;` `#` `/`, перевод строки, а также слова `доб`, `доп`, `вн` (точка после `вн`
   необязательна, поэтому под правило попадает и `внутр.`) и `ext`. Шаг критичен по порядку:
   если сначала выдернуть цифры, добавочный приклеится к основному номеру и даст
   несуществующий ключ (`8-495-556-45-95, доб. 422` → `5564595422`).
3. **Каждый кусок обрабатывается независимо** шагами 4–6. Никаких порогов и догадок,
   добавочный это или второй номер: короткий кусок сам отсеется по длине, а настоящий второй
   телефон даст свой ключ.
4. **Извлечение цифр** — удалить всё, кроме `0-9`.
5. **Отсев коротких** — меньше 10 цифр — ключа нет.
6. **Приведение к 10 цифрам** — взять последние 10. Для российских 11-значных это отбрасывает
   ведущую `7` или `8`, для 12 и более — код страны.
7. **Дедупликация** в пределах записи.

Нормализация — **чистая функция без исключений и списков**. Она не решает, «хороший» номер или
«плохой»: что дали, то и превратила в ключ. Номера-заглушки вроде `+7 999 999 99 99` дают
обычный ключ; неоднозначность (по ключу нашлось много записей — заглушка, номер приёмной,
колл-центр) разбирается на шаге сопоставления номера с записью в COREDEV-510, а не здесь.
Списки запрещённых номеров сознательно не ведутся: перечислить все заглушки невозможно, а
защита на стороне сопоставления покрывает и их, и остальные случаи.

## Эталонная реализация

Ниже — скрипт атрибута `phoneDigits` типа `opportunity` дословно.
Блок сверяется с YAML автотестом `PhoneDigitsContractDocTest`, поэтому разойтись с реальным
скриптом он не может.

```js
// Normalized 10-digit lookup keys of every phone of the record, see ECOSCRM-106.
// The collectPhoneKeys function below must stay character-identical to its copies in
// ecos-datalist/model/type/ecos-counterparty.yml and in the Mango route of COREDEV-510:
// a divergence in any step makes the keys differ and the lookup silently miss.
function collectPhoneKeys(raw, target) {
    if (raw === null || raw === undefined) {
        return;
    }
    // split before extracting the digits: the other way round an extension glues
    // itself to the main number and produces a key that does not exist
    var parts = ('' + raw).split(/[,;#\/\r\n]|доб|доп|вн\.?|ext/i);
    for (var p = 0; p < parts.length; p++) {
        var digits = parts[p].replace(/[^0-9]/g, '');
        if (digits.length < 10) {
            continue;
        }
        var key = digits.substring(digits.length - 10);
        var known = false;
        for (var k = 0; k < target.length; k++) {
            if (target[k] === key) {
                known = true;
                break;
            }
        }
        if (!known) {
            target.push(key);
        }
    }
}

var result = [];
// deal keeps a deprecated scalar `phone` beside `contacts`. It was left out at first
// because a sample of forty deals had it mirrored into contacts[0].contactPhone, but
// on the stand the deals that fill `phone` turned out to have an empty `contacts`:
// the number is there and no key is produced, so an incoming call never finds them.
// lead does not declare `phone` - value.load yields null there and the loop skips it.
var sources = [
    value.load('phone'),
    value.load('contacts[].contactPhone')
];
for (var s = 0; s < sources.length; s++) {
    var phones = sources[s];
    if (phones === null || phones === undefined) {
        continue;
    }
    if (typeof phones === 'string' || typeof phones === 'number') {
        phones = [phones];
    }
    for (var i = 0; i < phones.length; i++) {
        collectPhoneKeys(phones[i], result);
    }
}
return result;
```

Функция `collectPhoneKeys` — это и есть переносимая часть контракта: в скрипте контрагента она
лежит посимвольно такой же, различается только пролог: у контрагента он читает три
источника вместо двух, остальное совпадает:

```js
var result = [];
var sources = [
    value.load('phone'),
    value.load('cellPhone'),
    value.load('contacts[].contactPhone')
];
for (var s = 0; s < sources.length; s++) {
    var phones = sources[s];
    if (phones === null || phones === undefined) {
        continue;
    }
    if (typeof phones === 'string' || typeof phones === 'number') {
        phones = [phones];
    }
    for (var i = 0; i < phones.length; i++) {
        collectPhoneKeys(phones[i], result);
    }
}
return result
```

Внешнему потребителю (COREDEV-510) нужна `collectPhoneKeys` и вызов на одной строке — номер из
события Mango приходит в `from.number`:

```js
var keys = [];
collectPhoneKeys(fromNumber, keys);
// keys - ноль или несколько ключей; по каждому надо искать записи
```

Обратите внимание: результат — **список**, а не одно значение. Строка вида
`+7 903 234-41-35, +7 495 123-45-67` даёт два ключа, и оба законны.

## Как искать по номеру

Точечный путь через ассоциацию в предикате работает: `contains counterparty.phoneDigits <ключ>`
`ecos-data` разворачивает в подзапрос по таблице контрагента. Это отличается от пути внутрь
JSON-атрибута (`contacts.contactPhone`), который действительно срезается в `alwaysFalse` —
механизмы разные, путать их не надо. Поэтому достаточно одного запроса на источник:

1. Запрос к `emodel/deal` с предикатом
   `OR( contains phoneDigits <ключ>, contains counterparty.phoneDigits <ключ> )` — находит и
   сделку, у которой номер записан в своих контактах, и сделку, у которой он есть только у
   привязанного контрагента.
2. Если результат пуст — тот же запрос к `emodel/lead`. Приоритет: сначала сделка, затем лид.

Если ключей из номера получилось несколько, их можно передать списком в одном предикате:
`in phoneDigits [<ключ1>, <ключ2>]` — это тоже пересечение массивов и работает как «любой из».

Оба варианта проверены запросами к стенду: неверный ключ даёт ноль записей, то есть предикат
действительно применяется, а не игнорируется.

## Ограничения и подводные камни

- **Предикат по `phoneDigits` — это пересечение массивов, а не поиск подстроки.** Для multiple-
  колонки `ecos-data` строит `"phoneDigits" && ARRAY[?]`, и это верно для `contains`, `eq` и `in`
  одинаково. Значит искать можно только по целому ключу из десяти цифр: `9162042100` находит
  запись, а `+7 916 204-21-00` — нет. Это же ограничение видит пользователь в фильтре «Телефон»
  журналов лидов и сделок (колонка отображает человекочитаемый номер, а фильтрует по
  `searchConfig.searchAttribute: phoneDigits`). Подсказки об этом в интерфейсе пока нет —
  вопрос вынесен в раздел Post-Completion плана.
- **В расширенном фильтре по колонке «Телефон» годятся только условия «содержит», «равно» и
  «один из».** Для multiple-колонки `DbEntityRepoPg` умеет строить SQL только для `eq`, `contains`
  и `in`; на любом другом условии («начинается с», «заканчивается на», сравнения) метод возвращает
  `false`, и это условие **молча выбрасывается из запроса** — вместо ошибки или пустого результата
  пользователь получает весь список записей, как будто фильтр совпал со всеми. Условия
  `empty`/`not-empty` работают: они превращаются в проверку `array_length(col, 1) IS NULL`.
- **Сортировка и группировка по колонке «Телефон» идут по исходному пути, а не по `phoneDigits`:**
  подмену делает только `searchConfigProcessed`, а сортировка передаёт `column.attribute` как есть.
- **Фильтр по телефону работает в табличных журналах, но не на канбан-досках.** Подмену атрибута
  предиката по `searchConfig.searchAttribute` делает `JournalsConverter.searchConfigProcessed`,
  и вызывается она только из `journalsDataLoader`. Доски (`deal-board.yml`, `lead-board.yml`
  ссылаются на те же журналы) строят предикат в `sagas/kanban.js` без этой подмены, поэтому там
  по-прежнему уходит `contacts.contactPhone` и фильтр молча не находит ничего. Чинится это на
  стороне `ecos-ui`, отдельной задачей.
- **Третий журнал с такой же настройкой живёт в другом репозитории:**
  `ecos-crm-citeck/src/main/resources/app/artifacts/ui/journal/deals-community-journal.yml`.
  Выкладывать его можно только после выпуска `ecos-crm` с `phoneDigits`: без родительского типа
  атрибута в предикате не существует.
- **Значение пересчитывается при каждом сохранении записи** (`storingType: ON_MUTATE`). Поэтому
  `phoneDigits` добавлен в `excludedAtts` аспекта `history-config` у `deal`, `lead` и
  `ecos-counterparty` — иначе история событий засорялась бы техническими записями.
- **Скрипт на `opportunity` не читает `counterparty.phoneDigits`.** Иначе значение устаревало бы
  при изменении телефона контрагента без пересохранения сделки. Связь с телефоном контрагента
  даёт именно двухшаговый поиск, а не общий массив.
- **Депрекированное поле `deal.phone` тоже источник.** Сначала его решили не читать: в
  выборке из сорока записей `phone` дословно совпадал с `contacts[0].contactPhone`, то есть выглядел
  уже зеркалированным. На стенде эта посылка не подтвердилась: у сделок с заполненным `phone`
  список `contacts` оказался пустым — номер есть, а ключа нет вовсе, и звонок такую сделку не
  находил. Поэтому `phone` добавлен в пролог скрипта `opportunity`; сама `collectPhoneKeys` при этом не
  изменилась, так что требование симметрии трёх копий не затронуто. Атрибут объявлен только у
  `deal`; у лида его нет, и `value.load('phone')` там возвращает null, который цикл пропускает.
  Побочный эффект, который надо учитывать: если в `phone` лежит устаревший номер, а в `contacts` —
  актуальный, запись получит оба ключа и найдётся по обоим. Для поиска по входящему звонку это
  лучше пропуска: COREDEV-510 в любом случае обязан уметь разбирать несколько совпадений.
- **Контакт с нестандартными ключами не виден скрипту.** Модель описывает контакт полями
  `contactPhone`, `contactEmail`, `contactFio`; записи, созданные в обход модели с ключами
  `phone`/`email`/`fullName`, дадут «телефон в записи вижу, ключа нет». Это вопрос к данным, а не
  к скрипту.
- **Два номера в одном поле разделяются не любым символом.** Разделители перечислены в шаге 2
  алгоритма. Если номера разделены только пробелом или словом, цифры склеиваются в один кусок и
  дают ровно один ключ — по последним десяти цифрам склейки. Итог зависит от последнего номера:
  если в нём десять цифр или больше, ключ совпадает с его собственным, то есть последний номер
  найдётся, а все предыдущие потеряются («+7 495 556-45-95 и 8 916 117-77-16» → только
  `9161177716`); если цифр в нём меньше десяти, в ключ попадает хвост предыдущего номера, и
  получается ключ, которого нет ни у одного абонента («+7 495 556-45-95 и 630-20-10» →
  `5956302010`). Обе строки есть в таблице примеров выше. Пробел разделителем сделать нельзя —
  им же разделяют группы цифр внутри одного номера (`8 495 556 45 95`). Если в данных появится
  заметная доля таких значений, лечится это не расширением списка разделителей, а отбрасыванием
  кусков, где цифр заметно больше одиннадцати.
- **Табуляция разделителем не считается, хотя перевод строки считается.** В классе разделителей
  есть `\r` и `\n`, но нет `\t`. Номера, вставленные из таблицы или пришедшие выгрузкой CSV,
  разделяют как раз табуляцией, и тогда цифры склеиваются по общему правилу выше:
  `"+7 916 117-77-16\t+7 495 123-45-67"` даёт единственный ключ `4951234567`, первый номер
  теряется. Довод, по которому разделителем не сделали пробел (им разделяют группы цифр внутри
  одного номера), к табуляции не относится — внутри номера её не ставят. Правка меняет саму
  `collectPhoneKeys`, поэтому вносить её нужно одновременно в `opportunity.yml`,
  `ecos-counterparty.yml`, маршрут Mango из COREDEV-510 и листинг этого документа; вынесено в
  раздел Post-Completion плана.
- **Считать заполненность контактов счётчиком нельзя:** предикат `empty` на JSON multiple считает
  пустой массив `[]` непустым. Доли измеряются только выборкой.
- **План запроса на малом объёме — полное сканирование, и это нормально.** На таблице в сотню
  строк последовательное чтение дешевле индекса. На объёме, близком к промышленному (4288 сделок,
  728 контрагентов, 714 лидов), планировщик сам выбирает `Bitmap Index Scan` по GIN.

## Заполнение существующих записей

Значение вычисляется при сохранении, поэтому у записей, созданных до появления атрибута, оно
пустое до первого пересчёта. Пересчёт делают декларативные патчи, применяющиеся автоматически на
каждом стенде:

- `ecos-crm/src/main/resources/app/artifacts/app/patch/fill-opportunity-phone-digits.yml` —
  `typeRef: emodel/type@opportunity`, рекурсивно покрывает и лид, и сделку;
- `ecos-datalist/src/main/resources/app/artifacts/app/patch/fill-counterparty-phone-digits.yml` —
  `typeRef: emodel/type@ecos-counterparty`.

Оба создают запись `emodel/group-action@` с выборкой `admin-action-records-of-type` и исполнением
`update-calculated-atts` — то же самое, что действие «Обновить вычисляемые атрибуты» в интерфейсе
администратора («Инструменты разработки» → «Модули разработки»).

**Патч пересчитывает не только `phoneDigits`, поэтому выборка ограничена предикатом.**
Исполнение `update-calculated-atts` доходит до `ComputedAttsService.computeAttsToStore`, а тот
вычисляет **все** атрибуты типа, у которых `computed.storingType` не равен `NONE`. Атрибуты с
`ON_CREATE` и счётчики для уже существующих записей пропускаются, а `ON_EMPTY` вычисляется всякий раз,
когда текущее значение пустое. У `opportunity` такой атрибут есть — `dateReceived` («Дата создания»,
`SCRIPT { return new Date() }`, `storingType: ON_EMPTY`), и он наследуется лидом и сделкой. Запись с
пустым `dateReceived` получила бы датой создания момент прогона патча — необратимо и
автоматически на каждом стенде, куда патч доедет.

Поэтому выборка `admin-action-records-of-type` несёт предикат, исключающий ровно те записи,
которым пересчёт навредил бы:

```yaml
predicate:
  t: not
  val:
    t: empty
    att: dateReceived
```

Такая запись остаётся с пустым `phoneDigits` вместо того, чтобы потерять дату создания:
пустой `phoneDigits` чинится повторным прогоном, перезаписанная дата — ничем. Граница выбрана
в сторону восстановимого ущерба. На стенде предикат ничего не отсекает: записей с пустым
`dateReceived` там нет ни одной (`empty dateReceived` даёт `totalCount: 0` и по сделкам, и по лидам).
На промышленных данных патч затрагивает около пяти тысяч записей, и там такие записи могут
быть. **Чтобы охватить и их: посчитать записи с пустым `dateReceived`, заполнить им `dateReceived`
из `_created`, затем перезапустить патч поднятием `date`.** Без этого шага теряется только
поиск по телефону для этих записей, данные целы.

Связка «предикат закрывает каждый `ON_EMPTY`-атрибут типа» проверяется тестом
`PhoneDigitsFillPatchTest.selectionSkipsRecordsWithAnEmptyOnEmptyAttributeTest`: он читает
`storingType` из самого `opportunity.yml`, поэтому новый `ON_EMPTY`-атрибут, добавленный позже без
правки патча, уронит сборку, а не пройдёт незамеченным.

Повторный прогон патча безопасен и делается увеличением `date` либо кнопкой «Применить» в журнале
«Патчи». Порядок патча относительно выкладки самого типа платформой не гарантирован: если патч
отработает раньше, чем приедет тип с `phoneDigits`, он завершится успешно и ничего не заполнит —
это видно проверкой `records_query` по существующим записям и лечится перезапуском.

## Три копии алгоритма и как не дать им разойтись

Общего места для такого кода в платформе нет, поэтому `collectPhoneKeys` существует в трёх
репозиториях: `ecos-crm` (тип `opportunity`), `ecos-datalist` (тип `ecos-counterparty`) и
`ecos-crm-citeck` (маршрут Mango из COREDEV-510). **Расхождение хотя бы в одном шаге означает,
что ключи не совпадут и поиск будет молча промахиваться** — не с ошибкой, а пустым результатом.

Что удерживает копии вместе:

- в `ecos-crm` и `ecos-datalist` таблица примеров ECOSCRM-106 прогоняется тестами
  (`PhoneDigitsOpportunityTest`, `PhoneDigitsCounterpartyTest`) прямо по тексту скрипта из YAML —
  эталонной копии в тестах нет, YAML и есть источник правды;
- этот файл сверяется с YAML тестом `PhoneDigitsContractDocTest`, поэтому документация не может
  устареть незаметно;
- **тексты первых двух копий сверяет тест, а не ревью:** `PhoneDigitsContractDocTest` читает
  `collectPhoneKeys` из `opportunity.yml` этого репозитория и из `ecos-counterparty.yml` соседнего
  клона `ecos-datalist` и сравнивает их построчно, а заодно сверяет пролог контрагента из листинга
  выше с настоящим YAML. ⚠️ **Сравнение возможно только там, где соседний клон действительно лежит
  рядом, а на агенте Jenkins его нет:** `Jenkinsfile` — это `ecosBuild()` по одному репозиторию,
  поэтому в обычной сборке обе проверки пропускаются и зелёный CI ничего не говорит о симметрии
  копий. Чтобы получить ответ, которому можно верить, прогон запускается с флагом
  `mvn test -Dphonedigits.requireSiblings=true`: тогда отсутствующий или устаревший клон даёт не
  пропуск, а падение сборки с указанием, какого клона не хватает. Этот прогон обязателен перед
  выпуском версии и перед любой правкой алгоритма нормализации;
- **третья копия, в маршруте Mango, тестами этого плана не покрыта.** При её изменении таблицу
  примеров надо прогнать вручную или завести такой же тест на стороне маршрута.

## Особенности GraalJS, влияющие на код скрипта

Вычисляемые атрибуты исполняются на GraalJS (не Nashorn), через
`ru.citeck.ecos.commons.utils.script.ScriptExecutorImpl`.

- `value.load(...)` отдаёт `java.util.ArrayList` и `LinkedHashMap`. Опция
  `js.foreign-object-prototype` в GraalJS 24.2.2 включена по умолчанию и платформой не
  выключается, поэтому методы `Array.prototype` на загруженном списке работают. Полагаться на это
  всё же не стоит: скрипты написаны обычным циклом `for (var i = 0; ...)`, чтобы не зависеть от
  версии движка. Поведение закреплено тестом `ComputedScriptRunnerTest`.
- У загруженного JSON-объекта чтение по ключу работает, а **`Object.keys(obj)` возвращает пустой
  список** — перебрать поля объекта нельзя, обращаться можно только к заранее известным именам.
- Скрипт оборачивается в `(function(){…})()`, только если содержит подстроку `"return "` —
  с пробелом. `return[...]` не сработает.
- Массив доезжает до колонки без схлопывания за счёт поэлементной обработки в
  `RecordComputedAttsService.convertResult`: `mapAttributeTypeToRecordComputedResType` для TEXT
  про `multiple` не знает.
